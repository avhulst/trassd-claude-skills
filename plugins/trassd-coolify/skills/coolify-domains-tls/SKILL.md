# Coolify Domains & Automatic TLS

How to attach domains to a resource and let Coolify's reverse proxy obtain and
renew certificates automatically. Databases do **not** support domain
configuration — only applications and services do.

## FQDN format rules

Domain fields generate the proxy configuration based on these rules:

- Use full FQDN format including the protocol: `https://coolify.io`
- Multiple domains are comma-separated: `https://coolify.io,https://www.coolify.io`
- Add a port to map the proxy to a specific container port:
  `https://coolify.io:8080,http://api.coolify.io:3000`

Use the `https://` protocol to enable automatic HTTPS (see below). Use
`http://` only when you explicitly do not want TLS for that domain.

If a domain contains special or non-ASCII characters (`å`, `ä`, `ö`, `é`, …),
use its **punycode** form when configuring DNS and entering the FQDN, e.g.
`münchen.example.com` → `xn--mnchen-3ya.example.com`. Most DNS providers convert
this automatically, but switch to punycode manually if you hit issues.

## Required DNS records

You need an `A` record for every domain/subdomain pointing to your server's IP.
The same IP can serve many domains and subdomains.

```text
# Single domain (server IP 1.1.1.1)
example.com.        A    1.1.1.1
www.example.com.    A    1.1.1.1   # optional; redirect to apex inside Coolify

# Wildcard — covers every subdomain
*.example.com.      A    1.1.1.1
```

A wildcard `A` record lets you use any subdomain (`app.example.com`,
`api.example.com`, …) as an FQDN for any resource, including the Coolify
instance itself.

## Automatic HTTPS / Let's Encrypt

When you enter a domain with `https://`, Coolify does everything for you:

1. **Proxy configuration** — the reverse proxy (Traefik or Caddy) is configured
   to serve the app over HTTPS.
2. **Certificate issuance** — the proxy requests and installs a certificate from
   Let's Encrypt.
3. **Automatic renewal** — Let's Encrypt certs are valid 90 days and are renewed
   before expiry, handled seamlessly.

No extra action is needed beyond using `https://` in the domain field.

### Self-signed fallback (SSL warning)

If Let's Encrypt issuance **fails**, the Coolify Proxy serves a **self-signed**
certificate so the app stays reachable — but browsers show a security warning.
A self-signed cert or browser warning is the signal that ACME issuance did not
succeed; check DNS records, that port 80 is reachable (HTTP challenge), and the
Let's Encrypt rate limits / troubleshooting guidance.

## Path-based routing

Route one domain to multiple resources by appending a path:
`https://domain.com/path`, or with a port `https://domain.com:3000/path`.

Port placement matters — the port comes **after** the domain but **before** the
path:

- Correct: `https://coolify.io:3000/api`
- Incorrect: `https://coolify.io/api:3000`

More specific paths win automatically (`/api/v2/users` > `/api/v2` > `/api` >
`/` fallback), so multiple apps can share a domain without routing conflicts.

For path-based routing to work, the app serving a path must be **running and
healthy**. If it becomes unhealthy, requests to that path fall back to the app
serving the root domain (`/`).

## Wildcard & autogenerated domains

Set a **Wildcard Domain** on the server (`Server` settings, e.g.
`https://example.com`) together with a `*.example.com` `A` record. Coolify then
autogenerates domains for new resources:

- A random subdomain per app, e.g. `https://random.example.com`.
- Preview Deployment URLs, e.g. `https://<PRId>.random.example.com` (the preview
  URL template is editable on the application's `Preview Deployments` tab).

## Catching multiple domains (multitenancy)

With Traefik you can catch many domains by editing a resource's `Container
Labels` and using a `HostRegexp` rule. Note: the proxy **cannot** issue a
Let's Encrypt cert for a catch-all domain. For subdomains of one specific
domain, use a wildcard SSL certificate instead (see the `coolify-proxy` skill).

## DNS validation

Since `beta.191`, Coolify validates a domain's DNS records against Cloudflare's
`1.1.1.1` resolver. To use a different resolver, set
`Settings > Advanced > Custom DNS Servers` (comma-separated list). If a domain
is failing validation despite correct records, a custom/slow resolver or
propagation delay is a likely cause.

## Troubleshooting checklist

- Self-signed cert / SSL warning → ACME issuance failed: verify the `A` record
  points at the server, that HTTP challenge port 80 is publicly reachable, and
  Let's Encrypt rate limits.
- Domain not validating → check the `A`/wildcard record and `Custom DNS Servers`.
- Non-ASCII domain failing → use the punycode form.
- Catch-all domain has no valid cert → expected; use a wildcard certificate.
- Path route returns the wrong app → confirm the path's app is running and
  healthy (unhealthy paths fall back to `/`).
